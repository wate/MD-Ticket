課題管理ツール連携ガイド
=========================

MD-Ticketと、課題管理ツール(Redmine・Backlog・GitHub Issueなど)のチケットを連携するための取り決めです。
連携先ごとの違いは、`integrations/`配下のファイルにまとめています。

全体像
-------------------------

MD-Ticketは、作業中の書き換えをローカルで行い、作業の区切りで課題管理ツールへまとめて反映する作業の場です。
課題管理ツールでは、決定事項がコメントに散らばり、説明欄が古いまま残りがちです。
MD-Ticketの本文に最新の内容を集約し、ユーザーの承認を得て課題管理ツールの説明欄へ戻すことで、コメントをすべて読まなくても内容を把握できる状態を保ちます。

### 用語

- 連携先: MD-Ticketのチケットと紐付ける、課題管理ツール上のチケット(課題・Issue)
- 取り込み: 連携先の内容をMD-Ticketへ写すこと
- 反映: MD-Ticketの内容を連携先へ書き込むこと
- 管理先: 管理項目を正とする連携先
- 受付元: 依頼の窓口となる連携先のうち、管理先ではないもの

### 流れ

1. 取り込み: 連携先の件名と説明欄を取得し、種別のテンプレートに沿ってMD-Ticketを作成します
2. 紐付け: チケットファイルのフロントマターに`external`を書きます
3. 作業: 作業中の書き換えはMD-Ticketだけで行い、連携先へは都度反映しません
4. 反映: 作業の区切りで競合を確認し、説明欄とステータスを更新し、コメントを追記します
5. 記録: 反映後に連携先の更新日時を取得し直し、`updated_at`へ記録します

反映は、外部へ内容を書き込む操作です。
反映する内容と連携先をユーザーへ提示し、承認を得てから実行します。

連携手段に求める要件
-------------------------

連携手段は、REST API・MCPサーバー・CLI・エージェントスキルなど、課題管理ツールを操作できるものであれば種類を問いません。
提供元の公式の手段か、第三者製や自作の手段かも問いません。
利用者が、次の操作を行える手段を環境に合わせて選びます。

### 必須の操作

- チケットの取得: 件名・説明欄・管理項目・コメントを取得できること
- チケットの作成: 件名と説明欄を指定してチケットを作成できること
- チケットの更新: 説明欄と管理項目を更新できること
- コメントの追記: チケットへコメントを追加できること
- 更新日時の取得: 競合の確認に使うチケットの更新日時を取得できること

### 任意の操作

- 関連・親子の取得と設定: 対応しない場合は、説明欄やコメントに関連先へのリンクを書いて代替します
- 添付ファイルの取得と追加: 対応しない場合は、利用者が課題管理ツールの画面で取得・添付します

連携先ファイルの「参考情報」に公式の手段の例を載せています。
ただし、本ガイドの手順は、それらの手段があることを前提にしません。

ID管理規則
-------------------------

MD-Ticketのチケットと連携先の対応は、チケットファイルの先頭のフロントマターに`external`として記録します。
`external`は、連携先が1件でも常にリストとします。
フロントマターは連携先と紐付けたチケットにだけ書き、チケット種別のテンプレートは変更しません。

```yaml
---
external:
  - system: backlog
    id: 'PROJ-123'
    url: https://example.backlog.com/view/PROJ-123
    updated_at: '2026-10-18T09:00:00Z'
  - system: redmine
    id: '123'
    url: https://redmine.example.com/issues/123
    updated_at: '2026-10-18T10:30:00Z'
    primary: true
---
```

例は、Backlogを受付元とし、Redmineを管理先とする場合です。
各要素のキーは次のとおりです。

- `system`: 文字列・必須。連携先の課題管理ツールの種類で、連携先ファイルの名前と同じ値です(例: `redmine`)
- `id`: 文字列・必須。連携先のIDで、形式は連携先ファイルの「識別子の形式」に従います
- `url`: 文字列・任意。人が連携先を開くためのURLです
- `updated_at`: 文字列・初回の同期後は必須。最後に同期した時点の連携先の更新日時(ISO 8601)です
- `primary`: 真偽値・任意。連携先が2件以上のとき、管理先の1件だけ`true`にします

`id`は、数字だけの場合も引用符で囲んで文字列として書きます。
件名はMD-Ticketのh1に書き、フロントマターに件名のキーは設けません。

項目の対応付けの方針
-------------------------

項目ごとに、MD-Ticketと連携先のどちらを正とするかを決めます。
どちらを正とするかで、取り込みと反映の向きが決まります。

- 件名: MD-Ticketのh1と連携先の件名を対応させます。取り込み時は連携先の件名をh1に書き、MD-Ticketで変えた件名は反映時に連携先へ書き込みます
- 本文: MD-Ticketの本文を正とし、反映時に連携先の説明欄へ書き込みます
- 管理項目(ステータス・担当者・優先度・期日): 連携先を正とし、MD-Ticketには保持しません。必要なときに連携先から取得し、変更は反映時の操作として行います
- 種別: 連携先の種別と、MD-Ticketの種別(`task`・`bug`・`request`・`idea`)を対応させます
- コメント: 連携先にだけ置きます(「コメントの扱い」を参照)
- 関連と親子: 連携先を正とします(「関連と親子の扱い」を参照)

ステータス名や種別名などの値は、組織やプロジェクトごとに設定が異なります。
連携先ファイルでは「連携先のどの項目に当たるか」までを示し、値の対応は利用者がプロジェクトごとに決めます。
本文と連携先の説明欄で記法が異なる場合の扱いも、連携先ファイルに示します。

競合時の扱い
-------------------------

反映の前に連携先の現在の更新日時を取得し、`updated_at`と比べます。
連携先の更新日時のほうが新しい場合は、前回の同期以降に連携先が更新されています。
その場合は反映を止め、連携先の変更内容をユーザーへ提示し、取り込み直すか反映を続けるかを確認します。

反映が終わったら、連携先の更新日時を取得し直して`updated_at`へ記録します。
自分の反映による更新を、次回の競合として扱わないためです。
連携先が複数ある場合は、連携先ごとに`updated_at`で判定します。

コメントの扱い
-------------------------

連携先のコメントはMD-Ticketへ写さず、必要なときに連携手段で取得します。
コメントは連携先に残っており、写すと同じ内容を二重に持つためです。

コメントで確定した決定事項(仕様変更など)は、要点だけをMD-Ticketの本文へ反映し、出典としてコメントへのリンクを添えます。
本文へ反映するかどうかは、ユーザーが判断します。
競合の確認で前回の同期以降の更新を検出したら、新しいコメントを取得してユーザーへ提示し、本文へ反映する決定事項があるかを確認します。

連携先へコメントを追記するときは、作業の区切りでまとめた内容を1件のコメントとして書き込みます。

クローズ時の扱い
-------------------------

クローズのための専用の項目は設けず、連携先のステータスが終了扱いかどうかで判定します。
終了扱いのステータスを複数持てる課題管理ツールや、終了の理由を持つ課題管理ツールがあるためです。
終了扱いの判定と終了の理由は、連携先ファイルの「項目の対応」に示します。

- 連携先が終了扱いになった場合: MD-Ticketのクローズ(削除またはアーカイブ)を提案します
- MD-Ticketでクローズする場合: 連携先をどの終了ステータスまたは理由にするかをユーザーへ確認してから反映します

完了と却下のように意味の違う終了状態を、ユーザーへ確認せずに選びません。
クローズの手順そのものは、[チケットライフサイクル](ticket-lifecycle.md)に従います。

複数の連携先の扱い
-------------------------

1つのチケットを、複数の連携先と紐付けられます。
たとえば、クライアントの課題管理ツールに登録された課題をMD-Ticketで詳細に書き直し、自社の課題管理ツールで管理する運用です。
対応が終わったら、クライアント側へ結果を戻します。

- 管理先: `primary: true`を付けた連携先で、管理項目と関連・親子はこの連携先を正とします
- 受付元: それ以外の連携先で、コメントの確認と追記、完了の反映だけを行い、管理項目は書き換えません

連携先が1件の場合は`primary`を省略し、その1件を管理先とみなします。
2件以上ある場合は、`primary: true`を1件だけに付けます。
`primary`の付け替えは管理項目の正を切り替える操作のため、ユーザーの指示があった場合だけ行います。

説明欄を更新する連携先は、反映のたびにユーザーへ確認します。
受付元の説明欄には、クライアントの記載も含まれるためです。
受付元への完了の反映も、管理先の終了とは別にユーザーへ確認してから行います。

### 流れの例

1. 受付元のチケットを取り込み、MD-Ticketを作成します(この時点の`external`は受付元の1件です)
2. MD-Ticketで詳細を書き直します
3. 管理先にチケットを作成し、`external`へ`primary: true`を付けて追加します
4. 作業中は管理先と同期し、受付元のコメントは競合の確認のたびに確認します
5. 対応が終わったら、管理先を終了扱いにし、確認を得て受付元へ完了を反映します

関連と親子の扱い
-------------------------

関連と親子は、連携先(連携先が複数ある場合は管理先)を正とします。
MD-Ticket側は、既存の表現をそのまま使います。

- 親子: 子チケットを、親チケットと同名のサブディレクトリに置く配置で表します
- 関連: チケット本文の関連チケット欄に、種別とリンクで書きます

MD-Ticketの関連種別と、連携先の関連の対応の考え方は次のとおりです。
具体的な対応は、連携先ファイルの「関連と親子」に示します。

- 関連: 連携先の汎用の関連に対応させます
- 前提: 連携先の依存関係(先行・ブロック)に対応させます
- 派生: 連携先のコピー元・派生元の関連に対応させます
- 重複: 連携先の重複の関連、または重複を理由とした終了に対応させます

取り込み時に連携先で親が変わっていた場合は、子チケットのディレクトリを移すことになります。
移す前に、ユーザーへ確認します。
MD-Ticketで新しく作った子チケットや関連は、反映時に連携先へ追加します。

### 対応する種別がない場合

連携先に対応する種別がない場合は、汎用の関連で結べるなら結び、MD-Ticketの種別を本文の関連チケット欄に書きます。
汎用の関連もない場合は、連携先の説明欄またはコメントに関連先へのリンクを書いて代替します。

### 関連先が未取り込みの場合

関連先がMD-Ticketに取り込まれていない場合は、関連チケット欄に連携先のIDとURLだけを書きます。
関連先を取り込んだ時点で、MD-Ticketのチケットファイルへのリンクに書き換えます。

添付ファイルの扱い
-------------------------

MD-Ticketの`_files/`は、課題管理ツールの添付ファイルと対応させる前提の置き場所です。
添付ファイルを取り込む場合は、`_files/`に`{ticket-name}-{suffix}.{ext}`の名前で置きます。
置き場所と命名の詳細は、[参考資料管理](reference-files.md)に従います。

- 取り込み: 添付ファイルを自動で一括取得せず、取得するファイルをユーザーが選びます
- 機密情報: 機密情報を含む添付ファイルは`_files/`へ置かず、連携先へのリンクだけを本文に記録します
- 追加: 連携先への添付の追加は、ユーザーが明示した場合だけ行います
- 複数の連携先: 受付元の添付ファイルを管理先へ添付し直すかどうかは、ユーザーが判断します

接続情報の管理方針
-------------------------

接続先と秘密情報を分けて管理します。
連携先ごとの設定項目は、連携先ファイルの「接続情報」に示します。

- 接続先(課題管理ツールのURL、既定のプロジェクトなど): 設定ファイルに書きます
- 秘密情報(APIキー、アクセストークンなど): 環境変数、または連携手段が持つ標準の認証の仕組みに置きます
- MCPサーバーを使う場合: MCPクライアントの設定に接続先を書き、APIキーは環境変数や入力プロンプトから渡します

設定ファイルにAPIキーを直接書きません。
秘密情報を含むファイルを使う場合は、バージョン管理の対象から外します。

対象外の範囲
-------------------------

次の内容は、本ガイドの対象外です。
課題管理ツールの運用や、別の仕組みに委ねます。

- GitHubのプルリクエスト: 作成や紐付けはGitHubの運用に委ねます
- Wikiとの同期: チケットの連携とは別の関心事として扱いません

連携先の一覧
-------------------------

連携先ごとの違いは、`integrations/`配下のファイルにまとめています。
ファイル名は`system`の値と同じです。

- [Redmine](integrations/redmine.md): `system: redmine`
- [Backlog](integrations/backlog.md): `system: backlog`
- [GitHub Issue](integrations/github.md): `system: github`(Issueのみが対象です)

連携先ファイルは、すべて同じ見出し構成で書いています。
製品名やツール名は、各ファイルの最後の「参考情報」にだけ載せています。
